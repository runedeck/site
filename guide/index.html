Part I · Reference
ᚨ

The idea

Every AI coding harness wants its instructions in its own dialect and its own directory. Claude Code reads .claude/, Codex reads .codex/ and wants agents as TOML, Gemini CLI wants kebab-case filenames and its own tool names, opencode wants something else again. Copy the same markdown into each and you have four divergent copies within a month.

Rune Deck's answer is a build pipeline for prompts. You write a skill, agent, rule, or hook once as markdown with YAML frontmatter. The rune CLI transforms it per harness, deploys it, and records what it deployed, so drift becomes something you can detect and repair rather than something you discover.

The project's own framing of why raw copying is not enough: assembly (the deployed file is clean, the source keeps its metadata), provenance (an in-toto/SLSA record of which sources produced each deployed file), and manifest tracking (a fingerprint per deployed file, so modifications, staleness, and orphans are all visible).

The second idea, less obvious and more interesting: the same discipline is applied to the repository around the content. Architecture decisions are records under docs/decisions/, capability behaviour is specified in normative SHALL statements under docs/specs/, and both trees are managed by CLI subcommands rather than convention alone.

Worth knowing

The CLI repo was renamed from rune to cli. GitHub still redirects the old path, which is why Cargo.toml and the Homebrew formula both point at runedeck/rune and still resolve. rune is the binary name; rune-cli is the crate name; the library target inside it is called commands.

Lexicon

The vocabulary is deliberate and load-bearing: these words are directory names, config keys, and subcommands. Learning them is most of learning the tool.

TermMeaning
runeOne instruction file: a skill, an agent, a rule, or a hook. The closed set of kinds is skills, agents, rules, hooks.
deckA collection of runes: directories under runes/<domain>/ beneath a deck.yaml root. Each domain carries its own module.yaml.
castA named selection of runes across domains, for a use case. Lives at casts/<name>.yaml, supports extends, glob runes, and exclude.
targetThe repo rune deploys into. Bound with rune target so other commands know where to act.
.runeThe consumer manifest at a target's root: which source, which casts, which runes. Committed, so a selection is reproducible.
.manifestRune's own record inside each provider directory of exactly what it deployed, for drift detection, pruning, and repair.
qualified id<domain>/<kind>/<name>. Short forms are accepted while unambiguous; ambiguity is a hard error that lists every candidate.

There are exactly two roles, and most confusion about the tool comes from mixing them up: you author a deck, and you consume it in a target. rune context exists to tell you which one you are currently in.

Assemble and deploy

Two stages, always. rune assemble transforms source into build/<provider>/. rune deploy moves the build into provider directories and writes tracking. rune install runs both.

Source
  • rules/UseRTK.md
  • rules/claude/UseRTK.md
  • rules/user/UseRTK.md
  • agents/GameMaster.md
  • skills/MySkill/SKILL.md
Frontmatter intact. Qualifier directories still nested.
build/
  • build/claude/rules/…
  • build/gemini/… kebab-case
  • build/codex/… agents as TOML
  • build/opencode/…
  • *.yaml provenance sidecars
Strip frontmatter and reference links, resolve qualifiers, apply provider transforms.
Target
  • .claude/rules/…
  • .claude/skills/rune/…
  • .codex/ .gemini/ .opencode/
  • .provenance/*.yaml
  • .manifest
Skip unchanged, refuse modified without --force, prune orphans.

build/ is transient and rewritten on every assemble. Everything at the target is manifest-tracked.

Qualifier directories

Subdirectories in source are organizational, not structural: they flatten at assembly time, and the most specific wins. This is how one source file serves a personal override, a provider quirk, and a model-specific variant without branching.

DirectoryPurposePrecedence
user/Personal overrides and additions, git-ignored, merged at assemblyhighest
<provider>/<model>/Model-specific variant (claude-opus-4/)
<provider>/Provider-specific variant
(root)Base contentlowest

A file present only in user/ still deploys, flat, alongside the rest. That is the escape hatch that keeps individual customization out of upstream.

Providers

A provider is a config entry, not code. defaults.yaml is committed and carries the shipped conventions; a git-ignored config.yaml deep-merges over it, so a local override never edits a tracked file. Adding a harness means adding a stanza.

ProviderTargetAssemblyNotable
claude .claude (none) plugin: rune. Keeps the native SKILL.md fields Claude Code actually reads (allowed-tools, argument-hint, disable-model-invocation, and the rest). Alias claudecode.
codex .codex agents-to-toml, strip-links Deploy rule rulesync. Carries per-tier reasoning effort alongside model tiers.
gemini .gemini kebab-case-agents, remap-tools, strip-links The only provider that remaps tool names. Alias geminicli.
opencode .opencode kebab-case-agents, strip-links Model tiers point at Claude models.
agentskills .agents strip-links enabled: false. Opt-in generic fallback for the agentskills.io layout, via --provider or rune provider enable.

Each provider also declares keep_fields per kind (which frontmatter keys survive the strip), and models tiered as strong / fast / light so an agent definition can name a tier instead of a model id. target can be a map when a provider needs different roots per kind, with default as the fallback and unknown keys rejected.

Plugin shape

The sharpest recent design call. Skills deployed loose into .claude/skills/<name> load unnamespaced, so /deslop can collide with anything else on the machine, and nothing marks the content as the deck's.

Claude Code namespaces skills that arrive as a plugin, but the usual route to a plugin is a marketplace install, which is heavier than the primary path of staging and installing. The resolution: deploy the selection as a skills-directory plugin. Any directory under a skills directory carrying .claude-plugin/plugin.json auto-loads, no marketplace and no install ceremony.

  • Skills, agents, and hooks land under .claude/skills/rune/; rules keep their loose .claude/rules path, because rules are not a plugin component.
  • Deploy generates two manifest-tracked files at the plugin root: .claude-plugin/plugin.json and hooks/hooks.json, the latter a union of every deployed domain's hook table in sorted order. Hooks register through the loader instead of hand-wired settings.json entries.
  • Every skill then loads as rune:<name>. The ADR records this as verified live: claude plugin validate passes on the generated root, and a session lists the deck's skills under the namespace.
  • The target now carries two manifests, the loose rules tree and the plugin tree. Doctor scans the nested root as its own target and excludes it from the outer orphan scan.
  • plugin: null in config restores the loose layout.

Skill body edits are live in a running session; hook and agent changes need /reload-plugins.

Provenance and integrity

Two records answer two different questions, and keeping them separate is a stated architectural position.

Provenance

What produced this file? An in-toto Statement carrying an SLSA v1 provenance predicate, serialized as YAML, one sidecar per assembled file. Sidecars deploy into per-directory .provenance/ subdirectories at the target and ship inside release tarballs, so an extracted tarball can be verified without re-running assembly.

Manifest

Was this deployed file modified since we put it there? A .manifest dotfile at each target with a fingerprint per deployed file, referencing each sidecar by its provenance field. This is what makes incremental installs, pruning, and repair possible.

_type: https://in-toto.io/Statement/v1
subject:
    - name: claude/rules/AgentTeams.md
      digest:
          sha256: def456...
predicateType: https://slsa.dev/provenance/v1
predicate:
    buildDefinition:
        buildType: https://rune-cli/assemble/v1
        resolvedDependencies:
            - uri: rules/AgentTeams.md          # base
              digest: { sha256: abc123... }
            - uri: rules/user/AgentTeams.md     # override that won
              digest: { sha256: 789ghi... }
    runDetails:
        builder: { id: rune-cli, version: { rune: 0.1.0 } }

The sidecar names every input that combined to produce one deployed instruction, including which override applied.

The commands that read them

CommandQuestion it answers
rune provenanceShow the source-to-deployed chain for one file, or scan a directory for verification status grouped by source. --show-orphans includes files with no record.
rune driftDoes deployed content still match source? Also compares a source against an upstream reference, separating frontmatter from body and reporting which keys changed. --ignore suppresses expected per-project keys.
rune doctorPer-file integrity as ok / modified / missing / orphan. --repair restores missing files and quarantines orphans, and never overwrites a user edit.
rune cleanRemove files from previous installs that the current source no longer contains.
rune validateStructure, schemas, .mdschema compliance, plus manifest-based drift. Fast in-process by default; --scan adds gitleaks and semgrep and is reserved for commit and push hooks.

The asymmetry in repair is the design's ethical stance: an automated tool may restore what is missing and quarantine what is unaccounted for, but overwriting something a human edited takes a deliberate rune install --force. Orphans go to .trash/ rather than being deleted.

One validation subtlety worth internalizing: when a manifest exists, validate compares each tracked file against the current embedded template, not the fingerprint recorded in the manifest. The manifest indexes which files to check; the template is the source of truth for what they should contain. That is how a new CLI release can flag repos still carrying an old scaffold. Files that were already customized at init time never enter the manifest, so they never produce false drift.

The two flows

Consuming a deck

The dominant path. Bind a target, stage what you want, install, then verify.

# once per machine
brew install runedeck/tap/rune
rune setup                    # finds decks, persists choice
rune completion install
rune skill install            # teach agents to drive rune

# per project
rune init weather-stats --lang rust --purpose tool
rune target weather-stats
rune add --cast development   # or a domain, or an id
rune skill add deslop
rune context                  # confirm before writing
rune install
rune drift --target .
rune doctor --target .

Staging from a directory with no .rune asks before acting on the bound target. EOF, a closed stdin, and non-interactive runs all refuse the redirect.

Authoring a deck

Validate constantly, import upstream content with attribution, package per domain.

rune status --source <deck>    # one-shot dashboard
rune validate --source <deck>  # schemas + structure
rune validate --scan           # + gitleaks, semgrep

rune import <dir> --module <target> \
    --name <kebab-name> \
    --source-url <url> --dry-run

rune provenance --target <project>/.claude
rune release <domain> --source <deck>
rune dashboard --source <deck>

Tree import aligns SKILL.md to the target name, copies every companion byte-for-byte (scripts, binary assets, worker prompts), and regenerates a sidecar per file.

Aggregate operations matter at deck scale: run validate, provenance, drift, or clean against a deck root and they iterate every domain into one report, failing the run if any domain fails. Validation at deck level also refuses cross-domain deploy-path collisions, so two domains cannot both ship skills/X. There is no precedence rule to fall back on: the collision is simply an error.

Spec lifecycle

Rune adopts the OpenSpec standard as house canon without depending on the OpenSpec tool, and deliberately roots at docs/ rather than the hardcoded openspec/ directory. Interop is explicit: rune spec export --openspec and import --openspec convert between layouts without rewriting artifact bodies.

TreeHolds
docs/specs/<capability>/spec.mdCurrent truth. ## Purpose, then ### Requirement: blocks with normative SHALL statements, each carrying #### Scenario: blocks of WHEN/THEN bullets.
docs/changes/<change-id>/Proposed work: proposal.md, optional design.md, delta specs under specs/ using ## ADDED / MODIFIED / REMOVED Requirements, and tasks.md as a checklist.
docs/changes/archive/<date>-<id>/Completed or abandoned work, dated.
docs/decisions/ADRs, canonical for why a direction was chosen. Proposals link the relevant ADR; a design cites it rather than repeating its rationale.
 
rune spec propose improve-discovery --capability discovery
rune spec list                  # active changes; --specs for capabilities
rune spec show improve-discovery
rune spec context improve-discovery   # agent-ready work order
rune spec doctor                # relationship health, exit 1 on broken
rune validate
rune spec archive improve-discovery   # merges delta into current truth
rune spec archive improve-discovery --abandon

rune spec context is the entry point for an agent: it concatenates proposal, deltas, and checklist into one markdown work order with unchecked tasks highlighted, or structured JSON with id, proposal, deltas, and tasks. Archive refuses to run while tasks remain unchecked; -y overrides with a warning. Work that will not ship must still end explicitly, and abandoning stamps status: abandoned without merging anything.

Two restraints keep this from becoming ceremony for its own sake. Small local fixes are told to skip the change folder entirely and go through the ordinary edit, test, review loop. And when a scenario is already enforced by an executable check, the spec cites that check instead of restating it in prose.

ADR numbering is prefixed by area, managed by rune adr with per-prefix sequences: ASSEMBLY- for the pipeline, CLI- for command and interface decisions, RUST- for language conventions, DECK- for the source model, RUNE- for the fork and its governance. rune docs check then verifies internal links, unresolved wikilinks, and orphan pages, exempting the trees that spec, adr, and the backlog already manage.

TUI and dashboard

Two faces over one services layer, and a rule that neither may mutate state the CLI cannot reach.

Terminal UI (primary)

  • Vim keybindings modeled on tuicr. Miller columns navigate decks, then kinds, then runes; / filters in-pane, ! shows problems only.
  • Code view with counts (12j), gg/G/zz, section jumps, search with n/N, visual selection.
  • Review comments with c, persisted to .rune-comments.yaml at the target root as local working state. y copies the rendered review through pbcopy, falling back to terminal clipboard integration.
  • e edits in-TUI, E hands off to $EDITOR, o creates a user/ override.
  • A provenance tab showing the full SLSA statement per deployed rune, and --edit for a checkbox cast editor that can install from inside the UI.
  • Built on ratatui, crossterm, syntect, and edtui.

Web dashboard (read-only)

  • axum, askama, and htmx, bound to loopback, inspection only. Read-only and loopback-bound are an explicit security decision, not an implementation detail.
  • Views over deck content, artifacts, browse, files, and integrity.
  • Per-harness settings are surfaced through an allowlist of filenames in config (settings.json, config.toml, and similar). Anything unlisted, meaning caches, runtime state, credentials, stays hidden.

Both ship in the default `full` feature, so a plain cargo install gets the complete interface.

Stated as direction, not yet built

The ADR is candid that batched background log walking, the sliding metadata window, and the richer cast composition views are decided direction rather than implemented behaviour. The current TUI loads a short synchronous history window.

Extension model

A consistent principle runs through this area: the Rust kernel stays small and owns contracts, while capability lives in scripts and config. Three mechanisms implement it.

rune exec: scripts bundled in skills

A skill declares an exec: block in its frontmatter with script, optional runtime, and optional inputSchema / outputSchema. Rune resolves, launches, and validates; it does not create virtual environments or install packages.

ExtensionRuntimeWhy
.pyuv runNo venv orchestration in Rust
.sh .bashbash
.tsdeno runSelf-contained, implies no node_modules management
.js .mjsnode

Scripts receive RUNE_ROOT, RUNE_SKILL_DIR, the resolved RUNE_* ontology, CI=1, and INPUT_* variables derived from the top-level JSON input object. Because Rune invokes through an interpreter, scripts need no executable bit. In JSON mode output is wrapped as { ok, exit_code, structured, stdout, stderr }, and when outputSchema is declared, stdout must parse and validate against it. Schema validation sits in the kernel because it is a contract check, not a capability.

rune launch: an environment middleware chain

rune launch <tool> composes a LaunchPlan: child environment entries, an optional API base_url, command wrappers, and best-effort preflight steps. Middleware runs in the order named by --with a,b,c; a conflicting key warns and the later value wins. --tmux appends as the outer wrapper so it encloses everything before it. Built-ins cover pxpipe, otel, presidio, squid, docker, and tmux.

Unknown middleware foo resolves to an executable named rune-launch-mw-foo using the same search order as external verbs. Rune sends the current plan as JSON on stdin and merges the JSON patch from stdout, so middleware authors get a small contract instead of access to internals. The child receives only the composed environment; Rune's own is untouched. --dry-run prints the resolved plan and final argv without spawning anything.

Profiles layer on top rather than replacing the chain: rune launch claude@sol resolves a named preset contributing env, args, and with entries. Secrets are stored as from_env: KEY references resolved from the parent environment at launch, never as values, and an unset reference is a hard error. Profiles resolve from the user config only, because repo-level definitions would let an untrusted repository redirect credentials; that stays out until a restricted merge exists that forbids credential, endpoint, proxy, certificate, PATH, loader, HOME, and XDG_* keys from repository sources. Resolved values are covered by redaction in dry-run and JSON output.

External subcommands and discovery

An unrecognized verb falls back to a rune-<verb> executable, git-style, searched across module commands/, configured extension directories, and PATH. rune watch maintains a registry of monitored locations, local paths or remote repos pinned to a commit, and rune find ranks local and watched runes by name, trigger text, and description.

Config and sources

User config

One typed file at ~/.config/rune/config.yaml, deserialized into structs that deny unknown top-level fields, so a misspelled key fails loudly rather than silently doing nothing. Resolution order is RUNE_* environment variable, then config file, then built-in default, with a leading ~/ expanded after resolution. If the file is absent, everything resolves from environment and defaults, and no other file is consulted.

The config carries the shared ontology: the targets root, archive, vault, lore, mount, developer, artifacts, and git hooks locations, plus the top-level deck key that supplies the default source for staging. rune config prints the effective values with the provenance of each; get is raw and scriptable, exiting non-zero when unset. Key names stay short by convention, and the absence of a value is the default.

Where content comes from

A .rune entry names either a local path or a git source. Git sources are HTTPS only and pinned to a full 40-character commit SHA: no shorthand, no userinfo URLs, no branches, no tags. Clones go through gix into a content-addressed cache under ~/.cache/rune/git/, and the pinned tree is materialized into a per-SHA worktree. A fetch or checkout failure is a hard error, never a silent fallback.

Cast resolution happens at install time against the pinned commit, which is what makes a committed manifest reproducible: extends unions depth-first with cycles as an error, globs match canonical ids rather than paths, exclude applies last, and ordering is deterministic (domain, then kind, then name) specifically so drift reports stay quiet. Schema v2 adds a dirs: section declaring workspace members with strict relative-path validation, which lets rune todo --all aggregate across them.

Security posture in the details

The pattern repeats throughout: path traversal components in a manifest key are rejected rather than joined onto the target root, closing a write outside the deploy root through a poisoned .manifest. Remotely fetched scripts are verified by SHA-256 before execution. Third-party GitHub Actions are pinned to immutable refs. Secret scanning is scoped to the commit range a push introduces, with a full-history scan on a schedule instead of on every push.

Skeleton

Nothing in this repo runs on its own. It is the material rune init composes into a new repository. Read it together with the CLI, because the two are currently one redesign apart, and knowing which is which saves an afternoon.

What the CLI does today

A scaffold is three layers applied in order, each a hard requirement: base, then lang/<lang>, then purpose/<purpose>. A missing layer directory is an error rather than a skip.

rune init weather-stats --lang rust --purpose tool --brief "Warns the crew"
rune init ./existing-dir --lang shell     # scaffold in place
rune init weather-stats --dry-run         # print the plan, write nothing

--lang accepts rust, python, or shell; --purpose accepts tool, module, or spine. The skeleton root resolves as --skeleton, then RUNE_SKELETON or the skeleton config key (default ~/Developer/N4M3Z/skeleton), and if that directory does not exist, an embedded skeleton is materialized into a version-keyed cache. That fallback is why rune init works on a fresh machine with nothing checked out.

What the skeleton repo specifies

The published repo is a flat redesign: templates as siblings under templates/ with no dimensional grouping, selected by name with --with rust,tool, later templates overriding earlier files, and an interactive picker when none are named. Its template-composition spec is the most quietly elegant document in the org, and two of its rules deserve stealing regardless of this tool:

  • Composition never overwrites an existing file. That makes it idempotent, which makes the same command that scaffolds a new repo also retrofit an old one. Run it twice and the second run does nothing.
  • .gitignore is the single exception, and it concatenates. Fragment entries absent from an existing file are appended, entries already present are not duplicated. So a toolchain template contributes its ignores without discarding the base set, and retrofit and concatenation compose cleanly instead of fighting.
TemplateCarries
baseGit hooks, CI stub, Makefile, license, KEYS, editor and git config, agent briefs (CLAUDE.md, AGENTS.md), schemas for INSTALL and pull requests, ADR mdschema
rust · python · shell · nodeToolchain files plus that toolchain's .gitignore fragment, sourced from github/gitignore
tool · module · spineREADME shape and role-specific files

Placeholders resolve in both file contents and file names, which is why the shell template can ship a binary literally called bin/${NAME}: ${NAME} as the kebab-case slug, ${TITLE} as the human title, ${BRIEF} as a one-sentence description, ${OWNER} as the GitHub owner. Unknown placeholders are left verbatim rather than emptied.

Do not point the CLI at the repo yet

The published skeleton has no lang/ or purpose/ directories, so rune init --skeleton <clone> against it fails with a missing-layer error. The --with flag documented in its README does not exist in the shipped CLI. The repo was created weeks after the CLI's last push and represents where composition is going, not what runs today. Until the CLI adopts it, leave skeleton unset and use the embedded fallback.

Crew and ceremony

This is the part with no real equivalent elsewhere, and it may be the most transferable idea in the org. The work is done by a mixed crew of models with one human reviewer, and the governance is built around that fact rather than pretending otherwise.

Commit history on the CLI shows the arrangement plainly: the bulk authored by Sol (gpt-5.6-sol), a substantial share by the human owner, the rest by Claude Fable 5 and Grok. ADR frontmatter carries RACI fields, and several decisions record HarnessCouncil as consulted.

Attribution

Every commit must answer who wrote it, and which model, from the commit object alone. The orchestrating model goes in the author field; every other contributor, agent or human, gets a Co-Authored-By trailer in the same format: a display name ending in a parenthesized model id, plus a per-model non-routable address. A model working alone commits under its own identity with no trailer.

feat: resolve provider targets from module manifest

Co-Authored-By: Claude Fable 5 (claude-fable-5) <…>
Co-Authored-By: Codex (gpt-5.5) <…>

A ci/authorship check enforces it over the merge-base-to-head range, failing on an address absent from an authors.yaml allowlist, on a display name with no model id, on the author repeated as a contributor, and on an unresolvable merge base (rather than examining a partial range). Model commits are explicitly unsigned, and no branch rule requires signatures on main.

Review

Nothing merges on a single opinion. Automated bots comment on every pull request, at least one agent from a different vendor than the author reads the diff, and a human approves and merges. The skeleton's specification turns that into check runs: review/conventions and review/defects on every pull request, plus review/correctness on the owner's own (it spends the owner's subscription, so it is not required of anyone else). Each lane is backed by a different vendor. A lane that cannot produce a verdict stays pending rather than passing. Reviewer instructions load from the base branch, so a pull request cannot edit its own reviewers. Draft pushes skip the lanes entirely.

Deterministic checks (tests, lint, secret scan, schema validation, authorship, spec presence) are required independently: a passing review never substitutes for any of them, and every check binds the owner too, since the checks rules admit no bypass. A pull request touching protected paths must carry either a spec change or a spec:none label with a stated reason.

Traceability

Releases are sealed by an annotated owner-signed tag verified against a committed KEYS file before anything publishes, with tag creation restricted to the owner. And a Session: <harness>:<session-id> trailer on ceremonial commits means a bisected defect leads back to the session that wrote it, with checkpoint attachment adding the richer walk where it ran. Transcripts are written to the working layer, never into a repository.

Tension in the current documents

CONTRIBUTING.md says pull requests squash-merge, so the title becomes the commit message. The skeleton's review-ceremony spec says approved work enters main as a GitHub merge commit preserving every model author and trailer, and the session-recovery spec forbids merge strategies that rewrite commit ids because a rewritten id orphans its checkpoint. Those cannot all hold at once. The specs are the newer and more specific documents, so they probably represent the intended direction, but the contradiction is unresolved in the repos as they stand.

Positioning

The CLI keeps a parity matrix against with-logic/crew, pinned to a specific upstream commit and dated. Parity is defined honestly as "rune covers the capability its own way", and several rows are marked as covered differently or partial rather than claiming equivalence.

CapabilityRune's answer
Source refs with ref grammar sugarLocal paths or git HTTPS pinned to a full SHA in a committed manifest. Grammar sugar is a stated non-goal.
Registries as any git repo with a skills directoryDecks: structured repos with deck.yaml, domains, casts, and validation.
Resolved-SHA recording per installManifest fingerprints plus per-file SLSA sidecars, recorded in-tree.
Dependency graph in frontmatterNon-goal. Casts express grouping; dependencies between skills stay a deck-authoring concern.
Background autoupdatePartial by design. install re-materializes pinned sources, watch monitors locations, and no scheduler exists because deployment stays an explicit reviewable action.
Auto-detect harnesses and copy into eachA curated provider set with format conversion, not blind copies.
Atomic install with advisory lockPartial. Atomic temp-and-rename writes, but no cross-process lock: a single-operator tool by design.

The three non-goals are worth stating plainly, because they define the tool's shape more than any feature does: no project lockfile or npm-style dependency resolution between skills, no background autoupdate scheduler, and no blind per-harness copies without transformation.

Part II · Tutorials
ᛉ

Before you start

Thirteen walkthroughs, in three tracks: consuming a deck, authoring one, then process and extension. Each is self-contained apart from the stated prerequisite, and every command below was checked against the shipped argument definitions rather than the prose documentation, because in a few places those disagree.

Conventions that hold everywhere

ConventionDetail
--sourceA deck or rune source to read from. Defaults to . on almost every command.
--targetA base directory to deploy into, or a deployed tree to inspect. Each provider gets its own subdirectory beneath it, so --target ~ writes ~/.claude, ~/.codex, and the rest. Never pass --target ~/.claude.
--upstreamA second source tree to compare against. Mutually exclusive with --target on drift.
--jsonGlobal. Inspection commands emit structured output; staging commands print plain text.
--no-colorGlobal. Reaches every writer, so piped output stays clean.
Exit codes0 success, 1 errors occurred, 2 fatal. Worth branching on in scripts rather than grepping output.
Practice somewhere disposable

Several tutorials deliberately damage a deployed tree to watch the repair path work. Do them in a scratch directory, not in a repo you care about. Where a command writes outside the working directory, it is called out in the step.

Track A · Consuming a deck

1First run

Install the CLI and teach it where things live

Goal A working rune, a configured deck, shell completion, and an agent that knows how to drive the tool.

  1. Install. The formula compiles from source, so a Rust toolchain is pulled in as a build dependency and the first install is slow.

    brew install runedeck/tap/rune
rune --version    # version, build commit, build time

  2. Run guided setup. It discovers decks under your development directory and persists the choice. --defaults accepts everything without prompting, which is what CI wants.

    rune setup

    Expect A report of the deck it found, your target binding, and follow-up steps. Setup does not overwrite a choice you already made.

  3. Inspect and adjust the resolved configuration. get prints one raw value and exits non-zero when unset, which makes it safe in a shell conditional.

    rune config             # every key, with where each value came from
rune config path        # ~/.config/rune/config.yaml
rune config get deck
rune config set deck ~/Developer/runedeck/deck
rune config get targets # where `rune init <slug>` creates projects, default ~/Agents

    Expect Resolution order is environment variable, then config file, then built-in default. RUNE_DECK overrides the configured deck for one command without editing anything.

  4. Install completions. The installer writes to the shell's standard location and detects the shell from $SHELL when you omit it. It also clears the zsh compinit dump, so a stale cache cannot shadow the fresh script.

    rune completion install           # bash | zsh | fish | powershell | nushell
rune completion print zsh > /tmp/_rune   # or generate it yourself

  5. Install the agent skill. This writes a SKILL.md that teaches an AI coding CLI how to drive rune: which command to run first, which flags are safe to script, and which actions need a human.

    rune skill show                  # read it before installing
rune skill install               # default ~/.claude/skills
rune skill install --dir ./my-project   # project scope

    Expect With --dir, the argument is treated as a project root and the skill lands under <dir>/.claude/skills/rune/.

2Scaffold and deploy

From an empty directory to deployed instructions

Goal A new project carrying runes from a deck, deployed to every provider. Needs Tutorial 1.

  1. Scaffold. A bare slug creates the project under your configured targets root; an existing directory is scaffolded in place. Preview first: --dry-run prints the full plan including side-effect steps.

    rune init weather-stats --lang rust --purpose tool \
    --brief "Warns the crew" --dry-run
rune init weather-stats --lang rust --purpose tool --brief "Warns the crew" --bind

    Expect ~/Agents/weather-stats with hooks, CI, Makefile, licence, and agent briefs, git initialized. --bind makes it the active target in the same step.

  2. Bind the target if you did not use --bind. Binding is what lets you run staging commands from anywhere.

    rune target weather-stats     # slug, path, or <owner>/<name>
rune target --list            # recent targets, active one marked
rune target -                 # jump back to the previous target
rune target                   # show the current binding

  3. Stage what you want. Three granularities, all writing into the same .rune manifest. Staging does not install.

    rune add --cast development              # a named selection
rune add meta                            # a whole domain
rune add meta/skills/rune                # one fully qualified id
rune skill add deslop,version-control    # by bare name, comma-separated
rune agent add TheOpponent
rune rule add Deslop

    Expect An ambiguous bare name fails loudly and lists every candidate; retry as <domain>/<name>. Adds are idempotent and rewrite .rune atomically.

  4. Browse before committing to a selection. A bare kind noun lists that collection with staged markers.

    rune skill        # every skill the deck offers, staged ones marked
rune rule
rune provider     # providers with enabled state, target, plugin
rune find review  # relevance search across local and watched sources
rune find review --kind skill

  5. Confirm where you are before writing anything. This is the command an agent should run first, and the one that saves you from deploying into the wrong repo.

    rune context
rune context --json

    Expect The acting root and role (consumer, deck, module, or plain), the target binding, the manifest selection, per-provider deploy state, active spec changes, and a suggested next: step.

  6. Install. In consumer mode the target defaults to the source, so from inside the project this needs no flags. Preview the pruning first.

    cd ~/Agents/weather-stats
rune install --dry-run     # what would be pruned, nothing written
rune install

    Expect .claude/, .codex/, .gemini/, and .opencode/ appear, each with a .manifest. Claude skills land inside the plugin root .claude/skills/rune/ and load namespaced as rune:<skill>.

  7. Verify, then make it a habit. These two are the whole maintenance story.

    rune drift --target .     # deployed content still matches source?
rune doctor --target .    # ok / modified / missing / orphan per file
3Read what landed

The four files that explain everything

Goal Be able to answer "where did this instruction come from?" without guessing. Needs Tutorial 2.

  1. Read your own manifest. This is the committed, reviewable statement of what the project draws.

    # .rune
version: 2
sources:
    deck:
        local: ../runedeck/deck
        # path: runes/science   # optional: scope to one domain
runes:
    deck:
        casts: [development]
        skills: [meta/skills/rune]
        agents: []
        exclude: [meta/skills/noisy-thing]
dirs:                         # schema 2 only
    - path: wiki
      role: wiki
      required: true

    Expect Unknown keys are rejected outright. dirs: requires version: 2, and its paths must be relative; machine-specific absolute paths belong in a gitignored .rune.local.

  2. Look at what was deployed, and at rune's record of it. The manifest is per provider directory, and the plugin tree carries its own.

    ls -a .claude
cat .claude/.manifest
cat .claude/skills/rune/.manifest
ls .claude/rules/.provenance/

  3. Trace one file back to its sources. The sidecar names every input that combined to produce it, including which override won.

    rune provenance --target .claude/rules/UseRTK.md
rune provenance --target .claude                    # scan, grouped by source rune
rune provenance --target .claude --show-orphans     # files with no record
rune provenance --target .claude --source-uri https://github.com/someone/skill

    Expect Orphans are files rune did not put there. In a shared directory that is normal; in a rune-managed one it means something else is writing.

  4. Get the same information as data. Every inspection command takes --json, which is how an agent or a CI job should read state.

    rune doctor --target . --json
rune status --json
rune drift --target . --json
4Pin a remote deck

Make a selection reproducible for everyone who clones

Goal Draw content from a deck over git, pinned so the same manifest always produces the same files.

  1. Resolve a commit to pin to. Nothing else is accepted: no branches, no tags, no shorthand, no userinfo in the URL, HTTPS only. A fetch or checkout failure is a hard error rather than a fallback.

    git ls-remote https://github.com/runedeck/deck main

  2. Stage against the pinned source. The --ref flag takes the full 40-character lowercase hex SHA.

    rune add meta/skills/rune \
    --source https://github.com/runedeck/deck \
    --ref 0123456789abcdef0123456789abcdef01234567

    Expect For a git source, unknown ids and ambiguous names are checked at install rather than at add, and rune prints a note saying so. Local sources resolve eagerly and fail immediately.

  3. Install. The pinned tree is cloned into a content-addressed cache and materialized into a per-SHA worktree, so repeat installs and other projects on the same pin cost nothing.

    rune install
ls ~/.cache/rune/git/          # RUNE_GIT_CACHE_DIR overrides this

  4. Upgrade deliberately. There is no autoupdate by design: bumping the pin is an edit to a committed file, so it shows up in review like any other change.

    # edit the `ref:` in .rune, then
rune install --dry-run
rune install
git diff .rune

  5. Keep an eye on sources you do not pin. The watchlist monitors locations so rune find can search them and you can see when something moved.

    rune watch add ~/Developer/runedeck/deck
rune watch git https://github.com/runedeck/deck --ref 0123456789abcdef0123456789abcdef01234567
rune watch list
rune watch remove ~/Developer/runedeck/deck
5Override and repair

Customize without forking, and recover from damage

Goal Learn the one rule that keeps this system coherent, then break a deployment on purpose and repair it. Needs Tutorial 2.

  1. The rule: never edit a deployed file. Provider directories are build output. Edit the deck source and reinstall, or add a user/ override. Everything below is a demonstration of what the tool does when you break that rule.

    # in the DECK, not the target
mkdir -p rules/user
cp rules/UseRTK.md rules/user/UseRTK.md
$EDITOR rules/user/UseRTK.md

    Expect user/ is git-ignored and wins over the base file at assembly. A file that exists only in user/ still deploys, flat, alongside the rest.

  2. Reinstall and confirm the override took, by reading the provenance rather than trusting the output.

    rune install
rune provenance --target .claude/rules/UseRTK.md

    Expect resolvedDependencies lists both the base file and the user/ file, so the sidecar records not just the result but the resolution.

  3. Now damage the deployment three ways and see each state reported distinctly.

    echo "hand edit" >> .claude/rules/UseRTK.md   # → modified
rm .claude/rules/SomeOther.md                 # → missing
touch .claude/rules/StrayFile.md              # → orphan
rune doctor --target .

  4. Repair conservatively. This restores what is missing and quarantines what is unaccounted for, and it will not touch your hand edit.

    rune doctor --target . --repair
rune doctor --target . --verify    # exits non-zero if anything is broken: use in CI

    Expect The missing file returns, the stray is quarantined, and the modified file stays modified. Overwriting a human edit takes a separate deliberate command.

  5. Decide what to do about the edit. Either promote it into the source as a user/ override, or discard it.

    rune install --force        # overwrite user-modified files

  6. Understand pruning and recovery. Removing a rune from your selection and reinstalling prunes it, but pruned files are quarantined rather than deleted.

    rune install --dry-run      # see the prune list first
rune install
ls .trash/                  # quarantined by UTC timestamp
rune install --no-prune     # leave stale files alone
rune clean                  # remove files from previous installs

    Expect --only <prefix> deploys a subset and implies --no-prune, because a partial deploy has no business deciding what is stale.

Track B · Authoring a deck

6Author a domain

Write a rune and validate it before anyone consumes it

Goal A valid module carrying a skill, an agent, and a rule, checked by the same validator CI runs.

  1. Scaffold a module. This is a different scaffold from the project one, reached through --module, and it conflicts with the language and purpose flags.

    rune init --module ~/Developer/my-deck-domain
cd ~/Developer/my-deck-domain
cat module.yaml

    Expect module.yaml, defaults.yaml, and the kind directories. Inside a full deck, a domain is just a directory under runes/ with a module.yaml whose name equals the directory name. There is no registry to edit.

  2. Write a skill. The name must be kebab-case and must equal its directory, matching what the loader enforces at runtime.

    # skills/weather-lookup/SKILL.md
---
name: weather-lookup
description: "Fetch and summarize station observations. USE WHEN weather, forecast, station data."
version: 0.1.0
---

# weather-lookup

Body long enough to actually instruct the model...

    Expect Validation rejects a PascalCase skill name at author time rather than letting it fail at load. Warnings also cover a name over 64 characters, a description over 1024, reserved words in names, angle brackets in frontmatter, a description with no trigger phrase, and a body too short to instruct.

  3. Validate constantly. The default run is in-process and fast; the scanning run is slow and belongs in hooks.

    rune validate                    # schemas, structure, mdschema, manifest drift
rune validate --scan             # + gitleaks and semgrep, for commit and push hooks
rune validate --source ../deck   # whole deck: every domain, one aggregate report

    Expect Validate refuses a root carrying neither deck.yaml nor module.yaml unless you pass --force, so a stray run cannot walk an unrelated directory. At deck level it also fails on cross-domain deploy-path collisions.

  4. Survey the whole deck at a glance, in the terminal or the browser. The dashboard is read-only and loopback-bound by design.

    rune status --source ~/Developer/runedeck/deck
rune tui --source ~/Developer/runedeck/deck
rune dashboard --source ~/Developer/runedeck/deck   # port 40000, falls back to 40001

  5. Package a domain for distribution. Against a deck root the domain argument is required, because a deck holds many.

    rune release my-domain --source ~/Developer/runedeck/deck
rune release --format cowork      # the assembled claude plugin tree as an upload zip

    Expect Tarballs include .provenance/ and .manifest, so an extracted tarball can be verified without re-running assembly.

7Import upstream

Adopt someone else's skill without losing the trail

Goal Bring an external skill into your deck with recorded attribution, then detect when the upstream moves. Needs Tutorial 6.

  1. Plan the import before writing anything. Always start here: it prints the fetch, the placement, and the sidecar without touching disk.

    rune import https://example.com/some/SKILL.md \
    --module . --name WeatherLookup --dry-run

  2. Import a single file, or a whole local tree. Tree import aligns SKILL.md to the target name and copies every companion byte-for-byte: markdown references, worker prompts, scripts, binary assets.

    rune import https://example.com/some/SKILL.md --module . --name WeatherLookup
rune import ~/Downloads/some-skill-dir --module . --name WeatherLookup \
    --source-url https://github.com/someone/their-repo

    Expect Every imported file gets its own regenerated sidecar. The upstream's own .provenance/ directories are ignored rather than copied. --source-url is how a local checkout still records where it came from.

  3. Import a companion file rather than a skill, or a different kind entirely.

    rune import https://example.com/reference.md --module . \
    --name WeatherLookup --companion Reference.md
rune import https://example.com/agent.md --module . --kind agent

  4. Compare against upstream later. Drift separates frontmatter from body and reports which keys changed, so expected per-project differences can be suppressed instead of drowning the signal.

    rune drift --upstream ../their-checkout
rune drift --upstream ../their-checkout --ignore project,author
rune drift --upstream ../their-checkout --ignore body   # frontmatter only
rune drift --upstream ../their-checkout --all           # show unchanged too

    Expect By default only drifted entries are listed, with identical ones counted. Deliberately ignored drift still shows, marked as expected, so suppression never becomes invisible.

8Variants and providers

One source, different instructions per harness and per model

Goal Give Gemini different wording from Claude, and a newer model different wording from an older one, without duplicating a file.

  1. Lay out the qualifiers. Subdirectories are organizational and flatten at assembly, most specific winning.

    rules/UseRTK.md                       # base, lowest precedence
rules/gemini/UseRTK.md                # provider variant
rules/claude/claude-opus-4/UseRTK.md  # provider + model variant
rules/user/UseRTK.md                  # yours, highest precedence

  2. Assemble without deploying, then read the build tree. This is the fastest way to understand what a transform actually does.

    rune assemble
find build -type f | head -40
diff rules/UseRTK.md build/claude/rules/UseRTK.md    # frontmatter and ref links gone
cat build/codex/agents/*.toml                        # markdown agent converted

    Expect build/ is transient and wiped on every assemble. Never put anything there you want to keep.

  3. Select a model variant explicitly, overriding each provider's configured default.

    rune assemble --model claude-opus-4
rune install --model claude-opus-4

    Expect The id must match config/models.yaml exactly, and it is ignored for providers that have no such variant.

  4. Narrow the deployment. Provider selection is repeatable, and the target is a base directory that each provider extends.

    rune install --target ~/project --provider opencode
rune install --target ~/project --provider claude --provider codex
rune install --target ~ --only rules/          # subset; implies --no-prune
rune deploy --target ~/project                 # from an existing build/, no reassembly

  5. Change the default provider set for a source. This writes into the local gitignored config rather than the committed defaults.

    rune provider                       # name, enabled, target, plugin
rune provider enable agentskills    # opt-in .agents layout
rune provider disable gemini

    Expect A disabled provider is still reachable with an explicit --provider, so disabling changes the default set rather than removing the capability.

  6. When you want files placed with no transformation at all, use copy. It has no manifest tracking, which means no drift detection and no pruning: a deliberate trade.

    rune copy --source ./my-domain --target ~/somewhere
rune copy --source ./my-domain --target ~/somewhere --skip-provenance

Track C · Process and extension

9Spec lifecycle

Propose a change, hand it to an agent, archive it

Goal Run one capability change from proposal to merged current truth, the way the CLI's own repo does.

  1. Decide whether you need the ceremony at all. The project's own guidance: use a change folder for multi-session or multi-file work, and send small local fixes straight through the ordinary edit, test, review loop.

  2. Propose. The change id is stable and kebab-case; capabilities are repeatable and default to the change id.

    rune spec propose improve-discovery --capability discovery
rune spec propose wide-change --capability discovery --capability search --design

    Expect docs/changes/improve-discovery/ with proposal.md, a delta spec per capability under specs/, and tasks.md. --design adds design.md, which later shows up in both show and context.

  3. Fill in the delta. Requirements are normative, scenarios are executable-shaped, and the change spec uses explicit operation headings.

    ## ADDED Requirements

### Requirement: Ranked Discovery

The system SHALL rank discovery results by name, then trigger text,
then description.

#### Scenario: Exact name match

- **WHEN** a query exactly matches a rune name
- **THEN** that rune sorts first

    Expect Link the relevant ADR from proposal.md. ADRs stay canonical for why; a design cites one rather than repeating it. Where a scenario is already enforced by an executable check, cite the check instead of restating it in prose.

  4. Survey the tree, then hand the work to an agent. context is the apply entry point: a single work order with unchecked tasks highlighted.

    rune spec list                      # active changes and task completion
rune spec list --sort progress      # least complete first
rune spec list --specs              # canonical specs with requirement counts
rune spec show improve-discovery
rune spec context improve-discovery
rune spec context improve-discovery --json

    Expect If a name is both a change and a capability, show disambiguates by listing both forms.

  5. Check the tree's health as work proceeds. This exits non-zero on a broken change, so it belongs in CI.

    rune spec doctor

    Expect A change missing its proposal or delta is an error. An empty checklist, or a complete-but-unarchived change, is a warning. Otherwise it reports the tree healthy.

  6. Archive. Normal archive merges the delta into current truth and refuses to run while tasks remain unchecked. Work that will not ship must still end explicitly.

    rune validate
rune spec archive improve-discovery
rune spec archive improve-discovery -y          # override unchecked tasks, with a warning
rune spec archive dead-end --abandon            # no merge; stamps status: abandoned

    Expect Both paths move the change into the dated archive. Abandoning performs no spec merge at all.

  7. Interoperate with OpenSpec tooling if you need to. Conversion moves the layout without rewriting artifact bodies.

    rune spec export --openspec     # write openspec/ from the native docs root
rune spec import --openspec     # bring an openspec/ tree back in
10Decisions and tasks

Keep the reasoning and the backlog inside the repo

Goal Record a decision, supersede it later, keep docs links honest, and track work without leaving the repo.

  1. Write a decision record. Numbering is per prefix and drawn from a configured set, so CLI- and ARCH- keep independent sequences.

    rune adr new "Launch Profile Composition" --prefix CLI
rune adr list      # every record with status
rune adr index     # regenerate the decisions index table

  2. Retire a decision properly. Superseding flips the old record's status and cross-links the replacement in both directions, which is what makes the trail followable years later.

    rune adr supersede CLI-0018 CLI-0021

  3. Check the docs tree. This catches broken internal links, unresolved wikilinks, and orphan pages, and it knows to exempt the trees other commands manage.

    rune docs check
rune docs dev      # local preview, shells out to `mint dev` when docs.json exists

    Expect changes/ and specs/ belong to rune spec, decisions/ to rune adr. Their members are reached through tooling, not page links, so they are not reported as orphans.

  4. Track tasks in plain todo.txt syntax at the repo root, with priorities, projects, contexts, and due dates.

    rune todo add "(A) fix the discovery ranking +rune @cli due:2026-08-01"
rune todo ls
rune todo ls +rune        # by project
rune todo ls @cli         # by context
rune todo ls "(A)"        # by priority
rune todo do 3            # complete by 1-based list position

  5. Move tasks between the repo and a notes vault. The transform runs both directions through one item model that preserves unknown extensions.

    rune todo obsidian > ~/vault/Inbox/rune.md   # emit Obsidian Tasks markdown
rune todo import ~/vault/Inbox/rune.md       # pull `- [ ]` lines back in
rune todo --all                              # aggregate across `dirs:` members

    Expect --all needs a schema 2 .rune with a dirs: section. A missing required member is an error; a missing optional one is noted and skipped.

11Review in the TUI

Read a diff, leave comments, hand them to an agent

Goal Use the terminal UI as a review surface and export the result as an agent-ready work order.

  1. Open it. From a target it shows your deployment; with an explicit source it shows the deck. ? opens the keymap, which is the real documentation.

    rune tui
rune tui --source ~/Developer/runedeck/deck
rune tui --edit     # straight into the consumer checkbox editor

  2. Navigate. Miller columns move deck, then kind, then rune; the code view is vim-shaped.

    /          filter within the current pane
!          show problems only
j k        move; 12j jumps twelve (Esc cancels a count)
gg G zz    top, bottom, center
[[ ]]      previous and next section
/ n N      search within the file
V          visual selection

  3. Comment and edit. Comments persist to .rune-comments.yaml at the target root as local working state, which new scaffolds already ignore.

    c          open the comment box (Enter saves, Tab cycles the kind)
e          edit in the built-in editor
E          hand off to $EDITOR
o          create a user/ override for this rune
y          copy the rendered review to the clipboard

  4. Export what you wrote. Markdown is the agent-ready form and carries the source lines each comment refers to.

    rune review list
rune review export --format markdown
rune review export --target ~/Agents/weather-stats

    Expect Without --target, both commands check the current directory first and fall back to the bound target.

  5. Inspect the TUI headlessly, which is how you script it or debug a layout without a terminal.

    rune tui --snapshot --width 120 --height 40
rune tui --snapshot --keys "j j <Enter>" --drill 2 --tab provenance
12Launch profiles

Start a coding tool through a composed environment

Goal Point a harness at a different model or endpoint, and stack observability or a proxy in front of it, without writing a shell wrapper.

  1. See what is available. A bare invocation lists known tools with their install state and any profiles you have defined.

    rune launch

  2. Define a profile in the user config. Secrets are references, never values: an unset reference is a hard error rather than a silent empty string.

    # ~/.config/rune/config.yaml
launch:
    profiles:
        claude:
            sol:
                env:
                    ANTHROPIC_BASE_URL: http://localhost:4000
                    ANTHROPIC_MODEL: gpt-5.6-sol
                    ANTHROPIC_API_KEY: { from_env: LITELLM_MASTER_KEY }
                args: []
                with: []
        codex:
            deep:
                args: ["-m", "gpt-5.6-sol", "-c", "model_reasoning_effort=xhigh"]

    Expect Profiles resolve from the user config only. Repo-level definitions are deliberately excluded so an untrusted repository cannot redirect your credentials.

  3. Always dry-run first. This prints the resolved plan and the final argv, with sensitive values redacted, and spawns nothing.

    rune launch claude@sol --dry-run
rune launch claude@sol --dry-run --json

  4. Compose middleware. Order is explicit and deterministic; a conflicting key warns and the later value wins. --tmux is appended last so it encloses everything before it.

    rune launch claude --with otel,presidio
rune launch claude --with docker --tmux=work
rune launch claude --direct                  # clear the configured chain
rune launch claude -- --resume               # args after -- go to the tool

    Expect Built-ins cover pxpipe, otel, presidio, squid, docker, and tmux. An unknown name foo resolves to an executable rune-launch-mw-foo, which receives the plan as JSON on stdin and returns a JSON patch on stdout.

  5. Two conveniences worth knowing: for ollama, a profile name with no matching profile is treated as a model, and any unrecognized verb falls through to an external executable, git-style.

    rune launch ollama@llama3     # dispatches `ollama run llama3`
rune mycommand --flag         # runs rune-mycommand if it is on PATH
13Scripts in skills

Give a skill executable capability

Goal Ship a script next to a skill's instructions and run it through a contract that validates its output.

  1. Declare the script in the skill's frontmatter, next to SKILL.md.

    # skills/weather-lookup/SKILL.md
---
name: weather-lookup
description: "Fetch station observations. USE WHEN weather, station data."
exec:
    script: fetch.py
    outputSchema: output.schema.json
---

    Expect Without an exec: block and without --script, the run exits with code 3 and tells you to declare one.

  2. Write the script. Rune invokes it through an interpreter chosen by extension, so it needs no executable bit and you pick nothing.

    .py          → uv run
.sh .bash    → bash
.ts          → deno run
.js .mjs     → node

  3. Preview the resolved command and the environment that will be injected.

    rune exec weather-lookup --dry-run

    Expect The child receives RUNE_ROOT, RUNE_SKILL_DIR, the resolved RUNE_* ontology, and CI=1.

  4. Run it. A JSON input object arrives on stdin and is also flattened into INPUT_* environment variables, so a shell script can read it without a parser.

    rune exec weather-lookup -- --station LKPR
rune exec weather-lookup --json '{"station":"LKPR","hours":24}'
rune exec weather-lookup --script alternate.sh -- --verbose

  5. Consume the result programmatically. In JSON mode the child's output is wrapped in a stable envelope that preserves the raw streams alongside the parsed value.

    rune exec weather-lookup --json '{"station":"LKPR"}' | jq .structured

    Expect The envelope is { ok, exit_code, structured, stdout, stderr }. When outputSchema is declared, stdout must parse as JSON and validate against the schema file, resolved relative to the skill directory. Rune never creates a virtual environment or installs a package on your behalf.

State of play

Read this section before you plan anything around the org. Everything above is real and documented; the following is what is actually usable today.

  • The CLI is substantial and moving fast. v0.5.0 is tagged, and the Unreleased section already carries launch profiles, provider enable/disable, the todo and ADR surfaces, docs link checking, OpenSpec interop, manifest schema v2 with workspace members, workshop init, and the plugin deploy shape. Version 0.4.0 is recorded as succeeding forge-cli 0.3.x, so the lineage predates the org by some months.
  • The deck is nearly empty. Only the meta domain publishes anything, and it publishes exactly one artifact: the rune skill that teaches an agent to drive the CLI. The development, council, and research domains carry a module.yaml, a README, and a license, with no skills, agents, or rules. casts/all.yaml selects meta/** and nothing else. The README is upfront about this: domains fill as artifacts pass adoption review.
  • Installation builds from source. No GitHub Releases are published on the CLI repo, so the Homebrew formula fetches the tag tarball and compiles it, with Rust as a build dependency. The formula's URL still uses the pre-rename repository path and works only because GitHub redirects it.
  • The skeleton repo is ahead of the CLI. Its README and template-composition spec describe flat, name-selected composition via --with rust,tool. The shipped CLI implements the earlier two-dimensional model, requiring base, lang/<lang>, and purpose/<purpose> layers that the published repo does not contain, and has no --with flag at all. Pointing --skeleton at a clone of the repo fails with a missing-layer error; the embedded fallback skeleton is what actually runs. This is the one gap likely to cost you real time.
  • Smaller documentation drift. The Tour prints 0.4.0 for rune --version while the crate is at 0.5.0, and the CLI README's project-start block still uses rune quest, which 0.5.0 renamed to rune target (kept as a hidden alias). The authors.yaml allowlist that the attribution check depends on is specified but not yet present in the skeleton, though the correctness review workflow is there, with its actions SHA-pinned. The embedded skeleton also carries a node toolchain layer that --lang cannot yet select.

The honest summary: this is a serious, unusually well-documented single-operator toolchain in a fast pre-1.0 phase, with the tool substantially ahead of the content it is built to distribute. If you want to use it, the CLI is the product. If you want to learn from it, the specs, ADRs, and the crew ceremony are where the transferable ideas are.
